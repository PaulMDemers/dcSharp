# dcSharp Development Runbook

This project is currently optimized around legal KallistiOS fixtures, deterministic CLI runs, and small emulator slices that can be regression-tested.

## Toolchain

KallistiOS is installed in WSL:

```bash
~/kos
~/kos-ports
~/sh-elf
```

Verify the SDK:

```bash
wsl -e bash tools/kos/verify-kos.sh
```

## Run Fixtures

Text summary:

```bash
dotnet run --project src/DcSharp.Cli -- run artifacts/kos/dcsharp_probe.elf --instructions 50000000 --trace-tail 40
```

JSON summary:

```bash
dotnet run --project src/DcSharp.Cli -- run artifacts/kos/dcsharp_timer.elf --instructions 50000000 --trace-tail 40 --json
```

Manifest regression run:

```bash
dotnet run --project src/DcSharp.Cli -- fixtures fixtures/kos.json --validate-only
dotnet run --project src/DcSharp.Cli -- fixtures fixtures/kos.json
dotnet run --project src/DcSharp.Cli -- fixtures fixtures/kos.json --filter input_idle
dotnet run --project src/DcSharp.Cli -- fixtures fixtures/kos.json --report-json artifacts/reports/kos-fixtures.json
dotnet run --project src/DcSharp.Cli -- media inspect path/to/disc.cue
dotnet run --project src/DcSharp.Cli -- media extract-boot path/to/disc.cue --out artifacts/retail/1ST_READ.BIN
dotnet run --project src/DcSharp.Cli -- media analyze-boot artifacts/retail/1ST_READ.BIN --out-descrambled artifacts/retail/1ST_READ.descrambled.BIN
dotnet run --project src/DcSharp.Cli -- media boot-smoke path/to/disc.cue --instructions 2000 --trace-tail 16 --stop-on-unmapped
```

Useful run options:

- `--instructions <count>` sets the execution budget.
- `--trace-tail <count>` controls how many final SH-4 steps are retained.
- `--vblank-interval <instructions>` controls the current synthetic VBlank cadence.
- `--vblank-interval 0` disables synthetic VBlank.
- `--controller a0:start,a,joyx=-12,joyy=13,ltrig=40,rtrig=80` maps a static controller state to a Maple address.
- `--controller-script "a0:0:none;200000:start,a"` maps an instruction-indexed controller script to a Maple address.
- `--controller-a start,a,joyx=-12,joyy=13,ltrig=40,rtrig=80` and `--controller-b b,ltrig=7` are compatibility shorthands for A0 and B0.
- `--controller-a-script "0:none;200000:start,a"` is a compatibility shorthand for A0 scripts.
- `--dump-framebuffer artifacts/video/framebuffer.png --framebuffer-size 320x240` writes the current RGB565 VRAM snapshot as a PNG.
- `--pvr-ta-log artifacts/logs/ta-stream.txt --pvr-ta-log-limit 512` writes a decoded PVR TA stream tail with original stream indexes, guest instruction PC when known, raw command kind, control/payload role, named payload slots, control value, and written value. The default limit is 4096 decoded writes.
- `--pixel-format rgb565` is accepted explicitly; RGB565 is currently the only framebuffer dump format.
- `--audio-wav artifacts/audio/probe.wav` writes a deterministic stereo PCM16 WAV from modeled AICA PCM16/PCM8 playback diagnostics plus Yamaha-style 4-bit ADPCM channel decode.
- `--media path` accepts raw 2048-byte sector images, 2352-byte CD-sector dumps, simple CUE sheets, and GDI descriptors with local data tracks.
- `media inspect path` loads raw/CUE/GDI media, reports synthesized GD-ROM geometry, lists CUE tracks when present, scans early candidate sectors for Dreamcast IP.BIN-style boot metadata, and prints fields such as area, product, version, boot file, software maker, and title. For CUE inputs it also scans adjacent `.bin` files in the same directory and reports boot-sector candidates, which helps diagnose dumps whose CUE points at a merged or incomplete file while numbered track files are also present. Use `--scan-sectors <count>` to widen or narrow the boot-sector scan and `--json` for structured output.
- `media extract-boot path --out output.bin` inspects the media, finds the IP.BIN boot filename such as `1ST_READ.BIN`, opens the ISO9660 filesystem from the selected media or an adjacent CUE boot candidate, resolves split-track boot extents into later adjacent track files when needed, and writes the boot file to disk. Use `--json` for scriptable metadata including source path, ISO extent, title, volume identifier, and byte count.
- `media analyze-boot path` accepts a CUE/GDI descriptor or an already extracted boot binary, compares the original bytes with the KallistiOS/Marcus Comstedt descrambled layout, reports ELF/startup-stub/opcode-sample heuristics, assumes the BIOS boot load address `0x8C010000`, and can write the descrambled candidate with `--out-descrambled`.
- `media boot-smoke path` accepts a CUE/GDI descriptor or an already extracted boot binary, selects the analyzed original/descrambled layout with `--layout auto|original|descrambled`, maps it at the BIOS boot address `0x8C010000`, seeds the full 16-sector IP.BIN at `0x8C008000` when media metadata is available, enters the IP.BIN executable bootstrap when present, and runs the normal emulator loop with the same run options as `dcsharp run`. For CUE directory fallback candidates, IP.BIN is rebuilt from each sector's 2048-byte payload instead of copied as contiguous raw 2352-byte CD data. Media IP.BIN entry also seeds a BIOS-like initial SR (`0x400000F0`), an initial VBlank event, retail boot directory/mode work-area bytes at `0x8C0080F0..FE`, and preserves low BIOS interrupt handler table writes so retail paths that leave `VBR=0` can dispatch IRQs through guest-installed callback handlers that receive the accepted event in banked `r4`, return through the firmware interrupt wrapper, and have the accepted ASIC source acknowledged. Override with `--initial-sr`, `--seed-initial-vblank`, or `--no-initial-vblank`, and tune event cadence with `--vblank-interval` when probing boot waits. It also reports the final general-purpose registers, scheduler timing, pending TMU/ASIC interrupt state, dumps labeled top stack words for the current BIOS soft-reset checkpoint, reports writes into key boot regions, and can stop at the first selected diagnostic boundary with `--stop-on-unmapped` or `--stop-on-device-domain <domain>`.
- Use `--memory-write-log <path>` / `--memory-read-log <path>` with optional repeated `--memory-write-address <start-end>` / `--memory-read-address <start-end>`, repeated `--memory-write-pc <start-end>` / `--memory-read-pc <start-end>`, and `--memory-write-limit <count>` / `--memory-read-limit <count>` to capture filtered guest memory accesses after program load and firmware stub installation. Runtime reads and writes include the current instruction PC when available, and P4 device-register logs include `pc=` for SH-4 hardware accesses such as TMU reads and writes. This is useful for retail checkpoints where the device log is quiet but a stack/work-area field should change. For example, watching `0x7E000FDC-0x7E000FDF` on the IP.BIN path captures only the initial `completion-flag` zero write. Watching DOA2's retail idle state word `0x8C30CA2C-0x8C30CA2F` showed the former PVR identity gate: before PVR ID/revision defaults it stayed at `5`; with `PVR_ID=0x17FD11DB`, `PVR_REVISION=0x11`, and a synthetic VBlank bit in `PVR_SYNC_STATUS`, it advances to `6` at `0x8C12EB3C`.
- `--trace-log artifacts/logs/trace.txt --trace-pc 0x8C010000-0x8C010100 --trace-log-limit 4096` writes a bounded filtered SH-4 trace. Repeat `--trace-pc` to capture several disjoint code ranges in one run. Add `--trace-instruction 58352160-58352200` to start or narrow capture by executed instruction number when a diagnostic log identifies a late retail checkpoint. Trace-log lines include `#<instruction>` for correlation with FPU, memory, and device logs. Trace capture preserves every instruction that matches the requested PC/instruction filters, while CPU fast-forwards can still collapse uncaptured loops outside the PC filter. SH-4 scalar and vector FPU traces keep their compact normal form for finite results, but append raw source operand bits when `fadd`, `fsub`, `fmul`, `fdiv`, `fmac`, or `fipr` produces `NaN`/`Infinity`; this keeps retail FPU probes diagnosable without expanding ordinary traces.
- `--fpu-anomaly-log artifacts/logs/fpu.txt --fpu-anomaly-kind nan --fpu-anomaly-limit 512` captures bounded `FR`/`XF` transitions into non-finite single-precision bit patterns after each SH-4 instruction. Use `--fpu-anomaly-kind all|nan|infinity` to include all non-finites, only NaNs, or only infinities, `--fpu-anomaly-instruction 92326080-92326200` to narrow capture around a known late checkpoint, `--fpu-anomaly-register fr7` to follow one FPU register, and `--fpu-anomaly-distinct` to keep only the first anomaly for each PC/register/kind tuple in repetitive retail loops. Each line records the instruction count, PC/opcode/trace, changed FPU register, old/new bits, anomaly kind, and `FPSCR`.
- `--fpu-write-log artifacts/logs/fpu-writes.txt --fpu-write-register fr6 --fpu-write-instruction 58705000-58706770 --fpu-write-limit 128` captures bounded `FR`/`XF` register value changes, including finite writes that later become non-finite inputs. Repeat `--fpu-write-register` to follow several `FR`/`XF` registers in one run. Use it with a narrow instruction window after an anomaly log identifies the consumer PC/register. Each line records the instruction count, PC/opcode/trace, changed FPU register, old/new bits, `FPSCR`, and nearest symbol when one is available. SH-4 FPU arithmetic now updates FPSCR cause bits for the current operation and sticky flag bits for invalid, divide-by-zero, overflow, inexact overflow, and always-inexact `FIPR`; finite-input overflow respects `FPSCR.RM` by saturating to the largest finite value under round-to-zero while preserving overflow/inexact status. Enabled FPU exception traps are still future work.
- `--fpscr-log artifacts/logs/fpscr.txt --fpscr-instruction 58706480-58720000 --fpscr-limit 512` captures bounded FPSCR changes plus explicit `fpscr` access instructions without disabling CPU fast-forwards through unrelated loops. Each line records the instruction count, PC/opcode/trace, decoded old/new FPSCR value, whether the entry is a status `change` or same-value `access`, and nearest symbol when one is available; decoded FPSCR text includes rounding mode, sticky flags, exception enables, current causes, and control bits such as `DN`, `PR`, `SZ`, and `FR`.
- `--fpu-snapshot-log artifacts/logs/fpu-snapshots.txt --fpu-snapshot-pc 0x8C0F9FAA --fpu-snapshot-instruction 58706480-58706780 --fpu-snapshot-limit 32` captures pre-instruction `FR`/`XF`, `FPSCR`, `FPUL`, `PR`, and `R15` snapshots at selected PCs or instruction windows. Repeat `--fpu-snapshot-pc` for multiple exact PCs/ranges. The snapshot stores the register state before the watched instruction executes, then annotates the entry with the executed instruction trace for correlation.
- `--fpu-memory-log artifacts/logs/fpu-memory.txt --fpu-memory-register fr6 --fpu-memory-instruction 58700000-58706800 --fpu-memory-limit 512` captures bounded SH-4 FPU memory transfers for `fmov.s`/`fmov.d` load/store forms, including direction, register, effective address, transfer size, memory value, `FPSCR`, instruction count, trace text, and nearest symbol when one is available. Repeat `--fpu-memory-register` to follow several `FR`/`DR` registers in one run, and use repeated `--fpu-memory-address <start-end>` filters to narrow the log to stack, work-area, or generated-table ranges.
- `--pc-profile-log artifacts/logs/pc-profile.txt --pc-profile-limit 256` captures a top-PC execution histogram for the run. Add `--pc-profile-instruction START-END` to profile only a late frontier window after a trace or retail summary identifies the interesting instruction range.
- `--device-log artifacts/logs/devices.txt --device-domain pvr --device-kind Write` writes filtered device accesses.
- `--json` or `--summary-json` emits structured output for scripts and regression checks.
- `fixtures --validate-only` parses and validates a fixture manifest without requiring built ELF artifacts.
- `fixtures --filter <name>` runs or validates only fixtures whose names contain the filter text.
- `fixtures --report-json artifacts/reports/kos-fixtures.json` writes a structured fixture report while keeping the text summary on stdout.
- `tools/probe-retail.ps1` reruns the local ignored retail-disc boot-smoke probes when `retail_discs/` is populated. It checks that DOA2, Rayman, and Legacy advance through IP.BIN framebuffer setup to the current system BIOS soft-reset checkpoint without unmapped stops. With `-LongDoa2`, it also verifies the longer DOA2 path reaches the current loaded-binary callback/IRQ checkpoint after the GD-ROM DMA-read sequence and observed busy-bit task waits. Legacy verifies the former `0x330441F0` corrupted-IP.BIN pointer/table blocker stays cleared under a longer local retail budget.

The fixture manifest keeps sample paths, artifact names, instruction budgets, optional `mediaPath`, static `controllers`, instruction-indexed `controllerScripts`, and expected serial/video/audio checks together. Fixture text and JSON reports include Maple transfer counts, grouped PVR TA list summaries, assembled PVR TA strip summaries across opaque, punch-through, and translucent lists, GD-ROM status/sector-mode/TOC/read summaries, plus scheduler VBlank, hardware tick, hardware batch, max batch, idle advance, idle wake, CPU fast-forward, and controller-script change diagnostics for timing comparisons. Manifests can also set optional Maple thresholds such as `minMapleTransfers`, `minMapleDeviceInfoTransfers`, `minMapleGetConditionTransfers`, `minMapleDmaBatches`, and `requireNoMapleDescriptorLimitHits`, GD-ROM thresholds and filters with `minGdromStatusCommands`, `minGdromSectorModeCommands`, `minGdromTocCommands`, `minGdromReadCommands`, `minGdromBytesRead`, `gdromStatuses`, `gdromSectorModes`, `gdromTocs`, and `gdromReads`, scheduler thresholds such as `minVblankEvents`, `minHardwareAdvanceTicks`, `minHardwareAdvanceBatches`, `maxHardwareAdvanceBatch`, `minIdleAdvanceTicks`, `minIdleAdvanceBatches`, `maxIdleAdvanceBatch`, `minIdleTimerWakes`, `minIdleVBlankWakes`, `minIdleInputWakes`, `minCpuFastForwardInstructions`, `minCpuFastForwardBatches`, `maxCpuFastForwardBatch`, and `minControllerScriptChanges`, CPU register expectations with `cpu`, device-domain thresholds with `minDeviceAccessDomains`, ASIC expectations with `requireNoAsicPendingInterrupt`, `asicPendingInterrupt`, and `asicEventRegisters`, timer expectations with `requireNoTimerPendingInterrupt`, `timerPendingInterrupt`, and `timerChannels`, current PVR register values with `pvrRegisters`, current AICA register values with `aicaRegisters`, and decoded AICA channel state/playback counters with `aicaChannels`. Use `--artifacts <path>` with the `fixtures` command when testing a different artifact directory.

`fixtures/kos.json` declares the local `fixtures/kos.schema.json` schema for editor validation and autocomplete. Keep the schema in sync whenever a new manifest field becomes part of the supported fixture contract.

KOS fixtures are usually unstripped. When `.symtab` or `.dynsym` is present, text and JSON summaries include nearest function names for stop PCs and trace-tail entries.

Generated framebuffer, trace, and device logs belong under `artifacts/` and stay out of git.

Run summaries also include CPU diagnostics for `GBR`, `VBR`, `SPC`, `SSR`, `FPSCR`, `TRA`, `EXPEVT`, and `INTEVT`, plus TMU channel diagnostics for current counter/constant/control/priority/pending state, plus scheduler diagnostics for synthetic VBlank events, hardware advancement ticks, coalesced hardware batches, max hardware batch size, idle-advance ticks/batches/wake reasons, CPU fast-forwarded instructions/batches, and controller-script state changes. The runner currently uses this batching after SH-4 `sleep` instructions, side-effect-free self-branch waits, and narrow taken backward `bt`/`bf` waits with read-only polling bodies to advance hardware directly to the next timer, enabled VBlank, or controller-script boundary. A guarded DOA2 slot-8 rts-stub callback completion now raises `0x8C2B6CEC` bit `0x20` when the task helper reaches `0x8C130728` with the observed slot table and poll status state. The runner also fast-forwards forward/backward store-and-`dt` clear loops, predecrement byte-copy `dt` loops, the exact DOA2 `0x8C10786E-0x8C107878` byte-fill loop, the exact DOA2 `0x8C10E60A-0x8C10E62C` unrolled word-copy return tail, the exact DOA2 `0x8C0FB1C0-0x8C0FB216` trig setup plus recurrence span, the observed not-taken `0x8C0FB216-0x8C0FB22C` post-trig return tail, the exact DOA2 `0x8C0FB1FE-0x8C0FB20E` single-precision FPU recurrence fallback, the exact DOA2 `0x8C1005A0-0x8C1005B4` two-vector scale loop, the exact DOA2 `0x8C100A7A-0x8C100AB6` interpolation loop, the common DOA2 `0x8C1006EC-0x8C10077C` color-pack path, the common DOA2 `0x8C100AC0-0x8C100BB2` color-byte pack return helper, the common DOA2 `0x8C10077C-0x8C100888` TA emit return helper, and the common DOA2 `0x8C0E1E08-0x8C0E1EB0` text glyph setup helper when trace and FPU diagnostic captures are not watching them. The TA emit fast-forward also requires the scheduler wake-boundary guard so it does not skip across timer, enabled VBlank, or scripted input boundaries while replaying P4/store-queue writes through the memory API. The hot IP.BIN copy and DOA2 clear/timeout fast-forwards can take partial batches when the remaining instruction budget is smaller than the remaining loop body.

Current local retail probes for DOA2, Rayman 2, and Legacy of Kain pass the shared IP.BIN splash/reset handoff into the loaded boot binaries. BIOS system function `0` is modeled as a soft-reset handoff to `0x8C010000` with a high-RAM stack and clears boot area mode byte `0x8C0080FE` after the handoff. System function `3` is modeled as the nonterminal check-disc/menu helper used by DOA2's boot path. DOA2 now clears the former `0x8C12ED28/2A` state wait: `0x8C30CA2C` advances from `5` to `6`, then a longer local run reaches IRQ9 acceptance at `0x8C0F8F70` with `VBR=0`. The low BIOS IRQ table now preserves guest writes such as `0x00000224 = 0x8C12BF20`, dispatches IRQ9/IRQB into retail callback handlers instead of faulting at `0x00000600`, passes the accepted event code in banked `r4`, and returns callback-style handlers through a firmware wrapper that restores `SSR/SPC` plus the interrupted `PR` and acknowledges the accepted ASIC source; boot directory/mode bytes `0x8C0080F0..FE` stay seeded for the post-IRQ path while `0x8C0080FE` is cleared on handoff to avoid re-entering IP.BIN. The BIOS boot-directory seed now falls back to root but can derive a media root directory such as `DOA2` from a matching ISO9660 volume/root-directory name, which lets DOA2 load its data directory instead of searching root for `spr_adx.bin`. Loaded media reports GD-ROM disc type `0x80`, reaches successful DMA reads without re-entering IP.BIN, translates raw CUE filesystem FAD reads through the `trackStart + 150` data-area bias, and reports the BIOS GD-ROM send/exec/check lifecycle as processing then completed; a long probe records 17 successful reads, including the DOA2 directory sectors, `sector=432123`, and a 33-sector `sector=412644` asset transfer. The former software busy-bit blocker around `0x8C130460` is now guarded and fast-forwarded when bit 0 of `0x8C2F67FC` is set, callback slot 7 is still the default no-op, DOA2's task-helper queues are empty, and the active queue head is one of the observed task-arena work items below `0x8C2F7640`; synthetic completion also frees the matched slot, clearing the later full-arena allocator scan at `0x8C12FD20`. A 650M run advanced through those waits, recorded `Boot binary: writes=103289`, and reached the recurring VBlank IRQ/default-event checkpoint around `0x8C12BF42` with pending source `0x0320`. SH-4 store queue writes to `0xE0000000-0xE3FFFFFF` are buffered per 32-byte queue and flushed by `pref @Rn` through QACR0/QACR1 address bits. When QACR area bits are zero, dcSharp currently routes the flush to the TA input aperture as a narrow retail fallback for MMU-backed SQ mappings; DOA2 writes zero QACR values before emitting TA-shaped SQ traffic, and this fallback keeps those packets visible to the PVR diagnostics until a fuller MMU model exists.

The current DOA2 retail 150M probe reaches the TA emit/color-pack frontier with 779,608 TA writes and 32,397 assembled sprite-shaped packets. Those packets are now surfaced in `media boot-smoke`, but their raw sprite coordinate words decode as non-finite SH-4 qNaN values such as `0x7FBFFFFF`, so summaries label them `preview=nonfinite` and the preview renderer skips them rather than painting a misleading single-pixel artifact. Assembled sprite summaries retain source PCs from their TA writes; the DOA2 150M source grouping now shows all 32,397 assembled sprites as `nonfinite` from header writes at `0x8C1007FA`, control writes at `0x8C10084C`, and payload writes across `0x8C10084C-0x8C100850`. A longer 300M no-trace run still reports `taSprites=190279, taSpritePreview=renderable:0/degenerate:0/nonfinite:190279`, so the next rendering frontier is to trace why retail is feeding only qNaN coordinates through this phase: likely earlier transform/FPU data generation, command grouping, or a missing PVR/TA state bit rather than texture sampling.

`tools/probe-retail.ps1 -Doa2SpriteProbe` runs the 150M DOA2 JSON checkpoint and asserts the current source group as `nonfinite:32397 pc=h:0x8C1007FA/c:0x8C10084C/p:0x8C10084C-0x8C100850`.

PC-tagged TA logs plus PC-filtered memory watches show the TA emit helper reads those qNaN coordinate words from dynamic source buffers such as `0x8C2B6BB0-0x8C2B6BCF` at `0x8C100808-0x8C10082E`. Writes to the same buffers come from the interpolation path around `0x8C100AAA-0x8C100AB2` and vector-scale path around `0x8C1005B2`. A focused trace with the interpolation fast-forward disabled still records `fipr` at `0x8C100A7E/0x8C100A98` consuming qNaN lanes and writing the same sentinel values, so the shortcut is not the immediate cause. The renderer bridge at `0x8C100530-0x8C10055A` shows the first helper call returning with `fr0/fr2/fr4/fr6` as `0x7FBFFFFF`, storing `fr0` at `0x8C10053A`, then reloading it at `0x8C100544` before the interpolation call. A first-call trace inside `0x8C0FB1C0-0x8C0FB22C` now narrows the origin further: the helper enters with `r4=0`, keeps the reduction values finite/zero, reaches `0x8C0FB216` with `r3=0` and `r6=0`, then executes `0x8C0FB218 fdiv fr3,fr4` as `0/0`, producing the SH-4 default single qNaN `0x7FBFFFFF` that returns through `fr0`. A renderer-entry trace shows why that helper argument is zero: `0x8C10044C` copies the entry object pointer from `r4` into `r13` (`0x8C2B6C00` in the 150M probe), the mode-2 lookup reads `[r13+0] = 0x100`, table base `[0x8C2F07CC] = 0x8C20B3D4`, zero table index from `[0x8C20B5D4]`, and data base `[0x8C2F07DC] = 0x8C20C094`, while `[r13+0x0C] = 0` selects the `0x8C1004F0` branch and `0x8C100534 mov.l @(0xA,r13),r4` loads `[0x8C2B6C28] = 0`. The current frontier is therefore upstream object/state initialization or intentional sentinel handling for the renderer object, not a bad fast-forwarded trig argument. A 150M controller-script probe with Start/A pulses at 30M, 70M, and 110M instructions still reaches `PC=0x8C10076E` with 27 successful GD-ROM reads and the same all-nonfinite sprite source group, so the immediate renderability issue does not appear to be a simple unpressed-menu path in that window.

The hot 150M profile after the renderer-object trace exposed a repeated DOA2 timeout loop at `0x8C104D4C-0x8C104D56`: it polls uncached AICA sound RAM at `0xA080005C` (`0x0080005C` physical) for a nonzero mailbox word, then exits through a fixed `0x00400000` count when the word remains zero in dcSharp's silence-safe AICA model. The loop now fast-forwards only under exact opcode/literal/register guards, only while the mailbox read remains zero, with partial skips clamped to scheduler wake boundaries and disabled when memory-read watches are active. This preserves the current guest timeout path while removing the former six-instruction loop from the DOA2 hot profile; it is also a signpost that fuller AICA ARM/mailbox behavior may eventually replace the timeout rather than just skipping it.

Textured sprite coverage decodes the packed 16-bit UV tail words from KOS-shaped sprite geometry, carries optional sprite `u`/`v` expectations in fixture manifests, nearest-samples non-twiddled or twiddled RGB565 sprite textures across rectangular and skewed sprite quads, applies ARGB4444 texture alpha source blending, and covers texture shading plus coordinate clamp/repeat/flip modes in the tiny preview path.

AICA summaries include current named register values plus recent register accesses. Channel summaries decode sample format, compressed/streamed metadata, sample stride, loop enable, sample address, loop points, pitch, pan/send nibbles, derived left/right balance, volume, key-on state, playback sample/byte counters, and active channel count while remaining silence-safe. ADPCM formats intentionally report a zero byte stride but advance sample positions and packed byte counters at two 4-bit samples per byte; optional WAV dumps synthesize modeled PCM16, PCM8, and Yamaha-style 4-bit ADPCM channels from those diagnostics.

Maple summaries capture DMA command/response names, destination labels, receive buffers, response sizes, decoded controller state for `GetCondition` responses, and per-DMA descriptor traversal diagnostics including malformed chains that hit the descriptor guard.

## Tests

Run normal tests:

```powershell
dotnet test dcSharp.slnx
```

Run the fast local check, including whitespace diff checks, fixture-manifest validation, and the unit suite:

```powershell
.\tools\check.ps1
```

GitHub CI runs the same fast path on `windows-latest`: restore, build, fixture-manifest validation, and the unit suite. It does not build KallistiOS samples or require generated ELF artifacts.

Run long KOS fixture checks:

```powershell
$env:DCSHARP_RUN_KOS_FIXTURES='1'
dotnet test dcSharp.slnx --filter DreamcastKosFixtureTests
```

Or run the same fast local check plus the full CLI fixture manifest:

```powershell
.\tools\check.ps1 -KosFixtures
```

Use `-FixtureFilter <name>` with `-KosFixtures` to run only matching CLI fixtures after the fast checks:

```powershell
.\tools\check.ps1 -KosFixtures -FixtureFilter input_idle
```

The fixture checks assume the corresponding ELF files already exist under `artifacts/kos/`. The test suite and CLI runner both read `fixtures/kos.json`.
