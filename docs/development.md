# dcSharp Development Runbook

This project is currently optimized around legal KallistiOS fixtures, deterministic CLI runs, and small emulator slices that can be regression-tested.

## Toolchain

KallistiOS is installed in WSL:

```bash
~/kos
~/kos-ports
~/sh-elf
```

Verify the SDK:

```bash
wsl -e bash tools/kos/verify-kos.sh
```

## Run Fixtures

Text summary:

```bash
dotnet run --project src/DcSharp.Cli -- run artifacts/kos/dcsharp_probe.elf --instructions 50000000 --trace-tail 40
```

JSON summary:

```bash
dotnet run --project src/DcSharp.Cli -- run artifacts/kos/dcsharp_timer.elf --instructions 50000000 --trace-tail 40 --json
```

Manifest regression run:

```bash
dotnet run --project src/DcSharp.Cli -- fixtures fixtures/kos.json --validate-only
dotnet run --project src/DcSharp.Cli -- fixtures fixtures/kos.json
dotnet run --project src/DcSharp.Cli -- fixtures fixtures/kos.json --filter input_idle
dotnet run --project src/DcSharp.Cli -- fixtures fixtures/kos.json --report-json artifacts/reports/kos-fixtures.json
dotnet run --project src/DcSharp.Cli -- media inspect path/to/disc.cue
dotnet run --project src/DcSharp.Cli -- media extract-boot path/to/disc.cue --out artifacts/retail/1ST_READ.BIN
dotnet run --project src/DcSharp.Cli -- media analyze-boot artifacts/retail/1ST_READ.BIN --out-descrambled artifacts/retail/1ST_READ.descrambled.BIN
dotnet run --project src/DcSharp.Cli -- media boot-smoke path/to/disc.cue --instructions 2000 --trace-tail 16 --stop-on-unmapped
```

Useful run options:

- `--instructions <count>` sets the execution budget.
- `--trace-tail <count>` controls how many final SH-4 steps are retained.
- `--vblank-interval <instructions>` controls the current synthetic VBlank cadence.
- `--vblank-interval 0` disables synthetic VBlank.
- `--controller a0:start,a,joyx=-12,joyy=13,ltrig=40,rtrig=80` maps a static controller state to a Maple address.
- `--controller-script "a0:0:none;200000:start,a"` maps an instruction-indexed controller script to a Maple address.
- `--controller-a start,a,joyx=-12,joyy=13,ltrig=40,rtrig=80` and `--controller-b b,ltrig=7` are compatibility shorthands for A0 and B0.
- `--controller-a-script "0:none;200000:start,a"` is a compatibility shorthand for A0 scripts.
- `--dump-framebuffer artifacts/video/framebuffer.png --framebuffer-size 640x480` writes the current RGB565 VRAM snapshot as a PNG.
- `--pvr-ta-log artifacts/logs/ta-stream.txt --pvr-ta-log-limit 512` writes a decoded PVR TA stream tail with original stream indexes, guest instruction PC when known, raw command kind, control/payload role, named payload slots, control value, and written value. The default limit is 4096 decoded writes.
- `--pvr-ta-sprite-texture-sample-log artifacts/logs/sprite-texture-samples.txt --pvr-ta-sprite-texture-sample-log-limit 32 --pvr-ta-sprite-status renderable` writes bounded VRAM texture samples for matching sprites. Each sprite records the preview fallback-average UV and the four vertex UVs, adjusted clamp/repeat/flip coordinates, nearest texel coordinate/index, byte offset, raw texel, decoded RGB565, decoded alpha, and in-bounds/sampleable state.
- `--pvr-ta-texture-mode-log artifacts/logs/texture-modes.txt --pvr-ta-texture-mode-log-limit 64 --pvr-ta-sprite-status renderable` groups sprites by raw texture mode words and prints the decoded base plus alternate candidate base interpretations from `mode2`/`mode3`. Each candidate reports whether it is in VRAM, the probed byte count, nonzero bytes, first nonzero byte, and first 16-bit word; this separates a bad texture-base decode from genuinely empty VRAM.
- `--pvr-ta-mode-table-log artifacts/logs/mode-tables.txt --pvr-ta-mode-table-log-limit 64 --pvr-ta-sprite-status renderable` joins sprite mode groups to watched memory reads/writes that look like guest-side TA mode table entries. Use it with `--memory-read-log` / `--memory-write-log` filters around the header emission and table setup PCs. Each row lists matching table bases whose 4-word header/mode sequence was read, plus writes to that table entry with producer PC/opcode/source formatting, which is useful when a retail title mutates a shared mode table before flushing store queues to TA.
- `--pvr-ta-sprite-source-log artifacts/logs/sprite-sources.txt --pvr-ta-sprite-source-log-limit 32 --pvr-ta-sprite-status renderable` writes grouped sprite source traces by header/control/payload PC range, header/control values, and mode payloads. Each group includes raw width/height ranges, fallback pixel coverage, per-vertex X/Y/Z/UV ranges, and first/last raw payload words, which is useful for following retail sprite coordinate generation upstream from the final TA packet.
- `--pvr-ta-sprite-sq-log artifacts/logs/sprite-sq.txt --pvr-ta-sprite-sq-log-limit 32 --pvr-ta-sprite-status renderable` joins decoded sprite packets to SH-4 store-queue producer writes. When this log is requested, the CLI automatically enables a bounded memory-write watch for `0xE0000000-0xE000005F` if no explicit memory-write watch is already active. Each matched entry records the decoded sprite, queue base, per-word SQ producer PCs/values/opcodes, decoded producer source/trace when known, payload words, raw size, fallback pixel count, and the later TA flush PC range.
- `--store-queue-flush-log artifacts/logs/sq-flushes.txt --store-queue-flush-log-limit 256` writes one row per SH-4 `pref` store-queue flush with the queue index, source SQ address, QACR register/value, resolved destination, producer PC, and eight 32-bit words. This is useful when texture or TA traffic is being routed through QACR and the raw `0xE0000000` producer writes are not enough to tell which PVR aperture received the flush.
- `--pixel-format rgb565` is accepted explicitly; RGB565 is currently the only framebuffer dump format.
- `--audio-wav artifacts/audio/probe.wav` writes a deterministic stereo PCM16 WAV from modeled AICA PCM16/PCM8 playback diagnostics plus Yamaha-style 4-bit ADPCM channel decode.
- `--media path` accepts raw 2048-byte sector images, 2352-byte CD-sector dumps, simple CUE sheets, and GDI descriptors with local data tracks.
- `media inspect path` loads raw/CUE/GDI media, reports synthesized GD-ROM geometry, lists CUE tracks when present, scans early candidate sectors for Dreamcast IP.BIN-style boot metadata, and prints fields such as area, product, version, boot file, software maker, and title. For CUE inputs it also scans adjacent `.bin` files in the same directory and reports boot-sector candidates, which helps diagnose dumps whose CUE points at a merged or incomplete file while numbered track files are also present. Use `--scan-sectors <count>` to widen or narrow the boot-sector scan and `--json` for structured output.
- `media extract-boot path --out output.bin` inspects the media, finds the IP.BIN boot filename such as `1ST_READ.BIN`, opens the ISO9660 filesystem from the selected media or an adjacent CUE boot candidate, resolves split-track boot extents into later adjacent track files when needed, and writes the boot file to disk. Use `--json` for scriptable metadata including source path, ISO extent, title, volume identifier, and byte count.
- `media analyze-boot path` accepts a CUE/GDI descriptor or an already extracted boot binary, compares the original bytes with the KallistiOS/Marcus Comstedt descrambled layout, reports ELF/startup-stub/opcode-sample heuristics, assumes the BIOS boot load address `0x8C010000`, and can write the descrambled candidate with `--out-descrambled`.
- `media boot-smoke path` accepts a CUE/GDI descriptor or an already extracted boot binary, selects the analyzed original/descrambled layout with `--layout auto|original|descrambled`, maps it at the BIOS boot address `0x8C010000`, applies the WinCE GD-ROM `0x800` payload offset for original-layout `0WINCEOS.BIN` images, seeds the full 16-sector IP.BIN at `0x8C008000` when media metadata is available, enters the IP.BIN executable bootstrap when present, and runs the normal emulator loop with the same run options as `dcsharp run`. For CUE directory fallback candidates, IP.BIN is rebuilt from each sector's 2048-byte payload instead of copied as contiguous raw 2352-byte CD data. Media IP.BIN entry also seeds a BIOS-like initial SR (`0x400000F0`), an initial VBlank event, retail boot directory/mode work-area bytes at `0x8C0080F0..FE`, and preserves low BIOS interrupt handler table writes so retail paths that leave `VBR=0` can dispatch IRQs through guest-installed callback handlers that receive the accepted event in banked `r4`, return through the firmware interrupt wrapper, and have the accepted ASIC source acknowledged. Override with `--initial-sr`, `--seed-initial-vblank`, or `--no-initial-vblank`, and tune event cadence with `--vblank-interval` when probing boot waits. It also reports the final general-purpose registers, scheduler timing, pending TMU/ASIC interrupt state, dumps labeled top stack words for the current BIOS soft-reset checkpoint, reports writes into key boot regions, and can stop at the first selected diagnostic boundary with `--stop-on-unmapped` or `--stop-on-device-domain <domain>`.
- Use `--memory-write-log <path>` / `--memory-read-log <path>` with optional repeated `--memory-write-address <start-end>` / `--memory-read-address <start-end>`, repeated `--memory-write-pc <start-end>` / `--memory-read-pc <start-end>`, and `--memory-write-limit <count>` / `--memory-read-limit <count>` to capture filtered guest memory accesses after program load and firmware stub installation. Add `--memory-write-changed-only` to suppress peekable watched writes whose new value equals `previous=`, which keeps broad zero-fill traces focused on state transitions. Add `--memory-write-distinct` or `--memory-read-distinct` to keep only the first watched access for each destination/source/value tuple, which collapses repetitive scheduler toggles and polls while preserving the first occurrence of each transition. Runtime reads and writes include the current instruction PC/opcode when available, decoded write source or read target registers for common SH-4 memory-transfer opcodes, watched writes include `previous=` when the destination is peekable memory, and P4 device-register logs include `pc=` for SH-4 hardware accesses such as TMU reads and writes. This is useful for retail checkpoints where the device log is quiet but a stack/work-area field should change. For example, watching `0x7E000FDC-0x7E000FDF` on the IP.BIN path captures only the initial `completion-flag` zero write. Watching DOA2's retail idle state word `0x8C30CA2C-0x8C30CA2F` showed the former PVR identity gate: before PVR ID/revision defaults it stayed at `5`; with `PVR_ID=0x17FD11DB`, `PVR_REVISION=0x11`, and a synthetic VBlank bit in `PVR_SYNC_STATUS`, it advances to `6` at `0x8C12EB3C`.
- `--memory-poke-pc PC:ADDRESS:VALUE` applies a one-shot 32-bit diagnostic patch immediately before the matching guest PC executes, and may be repeated. The patch changes emulator memory without entering the watched-write log, so producer traces still mean "guest wrote this." Use it for controlled branch experiments after a normal trace identifies a candidate gate, then document the exact synthetic inputs and reject them unless they expose a hardware-shaped missing behavior. For example, Sega Rally's WinCE constructor probe used `--memory-poke-pc 0x8C017B7E:0x8C1376DC:0x8C137708` to decode the nonzero `source +0x1C` branch without editing emulator code.
- `--memory-snapshot-log artifacts/logs/final-memory.txt --memory-snapshot-address 0x8C20C094-0x8C20C0C3 --memory-snapshot-max-bytes 256` writes a non-mutating final-memory snapshot for repeated address ranges after the run stops. It supports system RAM, VRAM/TA texture aliases, AICA RAM, operand cache RAM, BIOS vector table, and boot-ROM zero reads. Each range reports captured bytes, truncation, nonzero count, first nonzero byte, FNV-1a checksum, 16-byte hex rows, little-endian 32-bit words, and ASCII preview. This is useful for retail probes where the final table or asset-buffer contents matter more than every access that produced them.
- `--trace-log artifacts/logs/trace.txt --trace-pc 0x8C010000-0x8C010100 --trace-log-limit 4096` writes a bounded filtered SH-4 trace. Repeat `--trace-pc` to capture several disjoint code ranges in one run. Add `--trace-instruction 58352160-58352200` to start or narrow capture by executed instruction number when a diagnostic log identifies a late retail checkpoint. Trace-log lines include `#<instruction>` for correlation with FPU, memory, and device logs. Trace capture preserves every instruction that matches the requested PC/instruction filters, while CPU fast-forwards can still collapse uncaptured loops outside the PC filter. SH-4 scalar and vector FPU traces keep their compact normal form for finite results, but append raw source operand bits when `fadd`, `fsub`, `fmul`, `fdiv`, `fmac`, or `fipr` produces `NaN`/`Infinity`; this keeps retail FPU probes diagnosable without expanding ordinary traces.
- `--fpu-anomaly-log artifacts/logs/fpu.txt --fpu-anomaly-kind nan --fpu-anomaly-limit 512` captures bounded `FR`/`XF` transitions into non-finite single-precision bit patterns after each SH-4 instruction. Use `--fpu-anomaly-kind all|nan|infinity` to include all non-finites, only NaNs, or only infinities, `--fpu-anomaly-instruction 92326080-92326200` to narrow capture around a known late checkpoint, `--fpu-anomaly-register fr7` to follow one FPU register, and `--fpu-anomaly-distinct` to keep only the first anomaly for each PC/register/kind tuple in repetitive retail loops. Each line records the instruction count, PC/opcode/trace, changed FPU register, old/new bits, anomaly kind, and `FPSCR`.
- `--fpu-write-log artifacts/logs/fpu-writes.txt --fpu-write-register fr6 --fpu-write-instruction 58705000-58706770 --fpu-write-limit 128` captures bounded `FR`/`XF` register value changes, including finite writes that later become non-finite inputs. Repeat `--fpu-write-register` to follow several `FR`/`XF` registers in one run. Use it with a narrow instruction window after an anomaly log identifies the consumer PC/register. Each line records the instruction count, PC/opcode/trace, changed FPU register, old/new bits, `FPSCR`, and nearest symbol when one is available. SH-4 FPU arithmetic now updates FPSCR cause bits for the current operation and sticky flag bits for invalid, divide-by-zero, overflow, inexact overflow, and always-inexact `FIPR`; finite-input overflow respects `FPSCR.RM` by saturating to the largest finite value under round-to-zero while preserving overflow/inexact status. Enabled FPU exception traps are still future work.
- `--fpscr-log artifacts/logs/fpscr.txt --fpscr-instruction 58706480-58720000 --fpscr-limit 512` captures bounded FPSCR changes plus explicit `fpscr` access instructions without disabling CPU fast-forwards through unrelated loops. Each line records the instruction count, PC/opcode/trace, decoded old/new FPSCR value, whether the entry is a status `change` or same-value `access`, and nearest symbol when one is available; decoded FPSCR text includes rounding mode, sticky flags, exception enables, current causes, and control bits such as `DN`, `PR`, `SZ`, and `FR`.
- `--fpu-snapshot-log artifacts/logs/fpu-snapshots.txt --fpu-snapshot-pc 0x8C0F9FAA --fpu-snapshot-instruction 58706480-58706780 --fpu-snapshot-limit 32` captures pre-instruction `FR`/`XF`, `FPSCR`, `FPUL`, `PR`, and `R15` snapshots at selected PCs or instruction windows. Repeat `--fpu-snapshot-pc` for multiple exact PCs/ranges. The snapshot stores the register state before the watched instruction executes, then annotates the entry with the executed instruction trace for correlation.
- `--cpu-snapshot-log artifacts/logs/cpu-snapshots.txt --cpu-snapshot-pc 0x8C100BCE-0x8C100BD6 --cpu-snapshot-limit 64` captures pre-instruction general-purpose register and control-register snapshots at selected PCs or instruction windows. Repeat `--cpu-snapshot-pc` for multiple exact PCs/ranges. Use it when a watched write identifies the store instruction but the live source registers explain why the value was produced.
- `--fpu-memory-log artifacts/logs/fpu-memory.txt --fpu-memory-register fr6 --fpu-memory-instruction 58700000-58706800 --fpu-memory-limit 512` captures bounded SH-4 FPU memory transfers for `fmov.s`/`fmov.d` load/store forms, including direction, register, effective address, transfer size, memory value, `FPSCR`, instruction count, trace text, and nearest symbol when one is available. Repeat `--fpu-memory-register` to follow several `FR`/`DR` registers in one run, and use repeated `--fpu-memory-address <start-end>` or `--fpu-memory-pc <start-end>` filters to narrow the log to stack, work-area, generated-table, or producer-code ranges.
- `--pc-profile-log artifacts/logs/pc-profile.txt --pc-profile-limit 256` captures a top-PC execution histogram for the run. Add `--pc-profile-instruction START-END` to profile only a late frontier window after a trace or retail summary identifies the interesting instruction range.
- `--wince-syscall-log artifacts/logs/wince.txt --wince-syscall-log-limit 256` captures only odd negative Windows CE API thunk PCs such as `0xFFFFFD1F`. It reuses trace capture internally, so the log records the instruction number, decoded HLE trace, callback descriptor details, preserved callback context registers, and any later WinCE APIs that appear in long retail probes without requiring a broad `0xFFFF0000-0xFFFFFFFF` trace filter by hand.
- `--wince-scheduler-log artifacts/logs/wince-scheduler.txt` writes a compact decoded final snapshot of the currently traced Sega Rally/WinCE scheduler and KData work fields. It reuses final-memory snapshots internally, so it does not require memory read/write watches and does not disable CPU fast-forwards. Use it with longer WinCE retail probes to compare scheduler queue flags, wait deltas, advancing kernel counters, the current-thread pointer, dispatch-table slots at `0x8C1318A0`, the dispatch-ring head/tail, priority bytes, masks, selected queue state, and the callback/list roots probed by the WinCE startup callback at fixed instruction budgets. The `0x8C131884` KData word is also split into byte fields for the observed yield-request and critical-section/dispatch-guard flags at `0x8C131884` and `0x8C131885`; Sega Rally toggles those bytes independently around the restored-thread wrapper, and word writes can clear both at once. The log also captures the observed WinCE high-RAM allocation pages and low virtual module metadata page, then follows the current-thread, module/list-root, and captured nested object pointers to dump their nonzero object words when those pointers are live, including the current-thread saved wrapper return/SP/PR/SR context fields. Work-item-shaped nested objects with flags `0x00010004` include a concise summary and one resolved-object dump, which makes the `0x8C01AAA8` priority-bucket insertion visible without broad recursive logging. Descriptor-shaped nested objects also include a shifted region comparison for `+0x0C` versus `+0x20`, the expected `+0x0C + +0x18` derived base versus recorded `+0x38`, and whether the `+0x1C` copy-source field is null. The dispatch ring is summarized on one line with head/tail equality, priority bytes, masks, and selected queue fields; the yield handoff is summarized on one line with the yield/critical bytes, current-thread flags, current-thread work item, resolved bucket object, work-item return PC, and saved wrapper return/SP/PR/SR. The active object chain rooted at `0x8C1364B8` is summarized separately with cycle/unavailable/truncation guards. Descriptor summaries require a plausible WinCE runtime base, which keeps `0x00C0C0C0` arena-fill lookalikes from producing noisy false descriptor diagnoses.
- `--device-log artifacts/logs/devices.txt --device-domain pvr --device-kind Write` writes filtered device accesses.
- `--json` or `--summary-json` emits structured output for scripts and regression checks.
- `fixtures --validate-only` parses and validates a fixture manifest without requiring built ELF artifacts.
- `fixtures --filter <name>` runs or validates only fixtures whose names contain the filter text.
- `fixtures --report-json artifacts/reports/kos-fixtures.json` writes a structured fixture report while keeping the text summary on stdout.
- `tools/probe-retail.ps1` reruns the local ignored retail-disc boot-smoke probes when `retail_discs/` is populated. It checks that DOA2, Rayman, and Legacy advance through IP.BIN framebuffer setup to the current system BIOS soft-reset checkpoint without unmapped stops, and that Sega Rally 2 reaches the WinCE scheduler/list loop while logging the initial `WIN32.PerformCallBack` thunk. Sega Rally's current loop has guarded fast-forwards for the exact post-TMU-read timer-delta helper tail and scheduler return tail, so fixed instruction-limit PCs may shift within the same loop as those skips change. With `-LongDoa2`, it also verifies the longer DOA2 path reaches the current loaded-binary callback/IRQ checkpoint after the GD-ROM DMA-read sequence and observed busy-bit task waits. Legacy verifies the former `0x330441F0` corrupted-IP.BIN pointer/table blocker stays cleared under a longer local retail budget.
- `tools/probe-sonic.ps1` reruns the focused Sonic intro milestone probes for Sonic Adventure GDI, Sonic Adventure 2 CUE, and Sonic Shuffle GDI. Use `-AssertKnownFrontiers` to validate the current baseline, or omit it while iterating on fixes that are expected to move one title past its current frontier.

SH-4 store queue writes to `0xE0000000-0xE3FFFFFF` are buffered per 32-byte queue and flushed by `pref @Rn` through QACR0/QACR1 address bits. When QACR area bits are zero, dcSharp currently routes the flush to the TA input aperture as a narrow retail fallback for MMU-backed SQ mappings; DOA2 writes zero QACR values before emitting TA-shaped SQ traffic, and this fallback keeps those packets visible to the PVR diagnostics until a fuller MMU model exists.

PVR VRAM is modeled through the CPU VRAM aliases `0x04000000-0x047FFFFF` and `0x05000000-0x057FFFFF`, and through the TA texture-memory aliases `0x11000000-0x117FFFFF` and `0x13000000-0x137FFFFF`. KOS names the latter `PVR_TA_TEX_MEM` and `PVR_TA_TEX_MEM_32`; they matter for texture uploads via store queues or PVR DMA even when the CPU never touches the ordinary VRAM windows directly.

PVR DMA is modeled as an immediate SH-4 DMAC channel 2 memory-to-PVR transfer when `0xA05F6808` is written with bit 0 set. The model reads the source from `SAR2` (`0xFFA00020`), byte count from `0xA05F6804` with a `TCR2 * 32` fallback, destination from `0xA05F6800`, copies into TA input/YUV or PVR VRAM/texture apertures, clears the PVR start register, clears `TCR2` on success, and raises ASIC event `0x0013` (`ASIC_EVT_PVR_DMA`). Transfers are surfaced on the video snapshot/summary so retail probes can distinguish a missing upload from a decoded-but-transparent texture. A DOA2 150M run after this support still records no started PVR DMA in the current window: its observed `0xA05F6808` write is a clear/ready write, not a start.
